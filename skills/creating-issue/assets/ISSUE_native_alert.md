# Issue：以產品內通知取代非必要的 `window.alert()`

> 本文件是虛構範例；專案名稱、元件名稱與盤點數字僅用於示範 issue 的寫法。

## 問題

範例專案 `web-app` 仍散落著約 40 個 `window.alert(...)` 呼叫，多數用於「使用者完成某項操作後，顯示阻塞式瀏覽器訊息」的常態回饋。

專案已有可重用的產品內通知元件，但目前只有部分流程採用：

- `notify.success(message)`：用於不需使用者回應的成功通知
- `notify.error(message)`：用於可留在當前畫面處理的錯誤通知
- `confirmDialog(options)`：用於必須由使用者做出選擇的確認流程

同一類回饋同時使用瀏覽器原生 alert 與產品元件，導致互動方式與視覺體驗不一致。

## 為什麼是問題

1. **視覺不一致**——原生 alert 使用瀏覽器樣式，與產品介面脫節。
2. **不必要地阻塞操作**——「儲存成功」等通知不需要決策，卻要求使用者按下確認。
3. **連續訊息難以管理**——批次操作可能連續觸發多個 alert，使用者必須逐一關閉。
4. **遮蔽目前內容**——在小螢幕上，原生對話框可能蓋住使用者剛完成的操作結果。
5. **干擾鍵盤與輔助科技流程**——原生對話框會強制轉移焦點，增加操作負擔。

## 典型錯用案例

| 場景 | 現況 |
|---|---|
| 表單儲存成功 | `alert("儲存成功")` |
| 儲存失敗但可重試 | `alert("儲存失敗，請稍後再試")` |
| 批次匯入部分失敗 | 每筆失敗資料各自觸發一次 alert |
| 執行不可逆操作前 | 只顯示 alert，沒有讓使用者選擇取消 |

## 範圍

涵蓋使用者日常操作會接觸到的通知流程：

- 表單建立與編輯
- 檔案上傳與批次處理
- 清單操作與狀態更新
- 共用元件中的成功、警告與錯誤訊息

**不含**：使用者離開尚未儲存頁面時，由瀏覽器提供的離頁確認機制。該機制用途不同，需另行評估。

## 期望結果

- 不需要使用者決策的訊息，使用非阻塞式產品內通知。
- 需要明確選擇的流程，使用產品內確認對話框。
- 相同情境採用一致的通知類型與文案原則。
- 批次操作將重複訊息彙整為單一、可理解的結果摘要。

## 佐證

在正式建立 issue 前，應以實際專案盤點結果替換以下資料：

- `window.alert` 的實際呼叫數量與位置
- 現有通知及確認元件的使用情況
- 最常觸發 alert 的使用者流程
- 可重現的畫面、操作步驟或測試證據

沒有完成盤點的資料必須標示為「待驗證」，不得將範例數字當成事實。
